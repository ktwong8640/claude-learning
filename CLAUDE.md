# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Döstädning — a mobile-friendly Swedish Death Cleaning (estate cleaning) catalog app. Users attach up to 3 photos/videos (and up to 3 receipt images) to each belonging and assign it a disposition (Keep, Gift, Sell, Donate, Discard), then export a printable inventory for family/executors, and optionally sync items to Google Drive/Sheets. See [README.md](README.md) for the full feature list and data model.

## Architecture

Plain HTML/CSS/JavaScript, no build step, no dependencies, no backend server:

- `index.html` — single-page app shell with three views (Capture, Items dashboard, Export) toggled by `js/app.js`, a bottom tab bar, item detail modal, the live camera overlay markup (with a Photo/Video mode toggle and recording indicator), and the external Google Identity Services / API loader `<script>` tags.
- `css/styles.css` — dark slate + neon blue theme (CSS custom properties in `:root`), mobile-first.
- `js/db.js` — thin promise-based wrapper (`AssetDB`) around IndexedDB (`death-cleaning-db` / `assets` store). Each media item's `blob` (photo or video) is stored directly in the IndexedDB record.
- `js/google-sync.js` — optional Google Drive/Sheets integration (`window.GoogleSync`), detailed below. Degrades to reporting "not configured" if `js/google-config.js` doesn't exist, rather than throwing — the rest of the app must keep working without it.
- `js/app.js` — all UI logic: view switching, the capture form's two independent pending-media queues (`mediaController` / `receiptMediaController`, both instances of `createPendingMediaController()`, each rendering its own removable thumbnail strip and "X of `MAX_MEDIA_PER_FIELD` used" count before the item is saved, and enforcing the `MAX_MEDIA_PER_FIELD` (3) cap in `.add()` — it returns `false` rather than adding once full, so callers can report what happened; `refreshCaptureMediaButtons()` disables the relevant Camera/Gallery buttons once a queue is full), `attachMediaToAsset()` enforcing the same cap for already-saved items (slices incoming items to whatever room remains and reports how many were skipped), the currency selector (`getCurrencyList()` via `Intl.supportedValuesOf('currency')` with a static fallback, remembering the last-used code in `localStorage`), the live camera capture flow for both stills (`getUserMedia` → canvas frame grab) and video (`MediaRecorder`, 60s cap) with a shared review/retake step, dashboard filtering/search, the item modal (two separate galleries — item media and receipt media — each supporting adding more via camera or file picker, or removing individual items, plus a per-item Google sync button, and an **Edit** button that swaps the view for `renderEditForm()` — a form covering every non-media field, reusing the capture form's category `<select>` options and disposition/currency constants rather than duplicating them, wired to the same disposition-conditional show/hide pattern under `modal-edit-*` ids so it doesn't collide with the capture form's own `f-*` ids), the Google Drive sync card in the Export view (`renderGoogleSyncCard`), the printable estate summary (`window.print()` + `@media print`), and JSON backup/restore (each media blob, in both collections, round-tripped through a data URL).
- `manifest.json` / `sw.js` / `icons/` — makes the app an installable PWA on Android (Add to Home screen, standalone display, offline app-shell cache). `icons/*.png` are generated placeholder art (simple ring on the theme's dark/cyan colors), not hand-designed. `sw.js` uses a **network-first** fetch strategy (falls back to cache only when offline) specifically so deployed updates reach open tabs/installed devices immediately, without relying on everyone remembering to bump `CACHE_NAME` — still bump it when the precached `SHELL_FILES` list itself changes (adding/removing a file), since that list is only read at install time.

No frameworks, no ES modules (scripts are loaded as plain globals so the page keeps working from `file://`), no backend server — core cataloging is fully local to the browser via IndexedDB. Google Drive/Sheets sync is the one opt-in exception that talks to an external service, and it does so directly from the browser (see below), not through any server this project controls.

Camera capture (`btn-open-camera` in `app.js`, and the "Camera" button inside the item detail modal) uses `navigator.mediaDevices.getUserMedia` with `facingMode: 'environment'` by default; video mode also requests `audio: true`. This requires a secure context (`https://` or `http://localhost`) — it will fail (with a handled, visible error) on plain `http://<lan-ip>` or `file://`. There is no way for a web page to invoke a phone's native camera app (e.g. Samsung's) or its proprietary modes; this is the standard browser camera pipeline, which is the ceiling for what any web app can do. The "Choose from Gallery" button (plain `<input type="file" multiple accept="image/*,video/*">`) is the fallback and works everywhere regardless of secure-context.

`openCamera(targetAssetId, field)` is shared between the capture form and the item modal, and between the item-photo and receipt flows: called with no `targetAssetId`, a captured photo/video is pushed into the pending queue for `field` ('media' or 'receiptMedia'); called with an existing asset's id, it attaches directly to that saved asset's `field` via `attachMediaToAsset(assetId, items, field)` instead. `field === 'receiptMedia'` also hides the Photo/Video mode toggle and forces photo-only capture, since receipts aren't videos. `removeMediaFromAsset(assetId, mediaId, field)` mirrors this on the removal side. Assets saved before the multi-media feature (single `photo` Blob field) are migrated into the `media` array format automatically in `loadAssets()`; the old boolean `hasProof` field is dropped there too, in favor of `receiptMedia.length`.

### Google Drive & Sheets sync (`js/google-sync.js`)

Client-side only — authenticates as the signed-in user via Google Identity Services (`google.accounts.oauth2.initTokenClient`), not a service account, so there is no secret credential in this codebase to protect. Scopes requested: `drive.file` (the app can only see/write files it created, or that the user explicitly picked via the Google Picker below — not their whole Drive) and `spreadsheets` (read/write on any sheet the user's account can already access, once they connect it by ID/URL).

- **Config**: `js/google-config.js` (template at `js/google-config.example.js`) sets `window.GOOGLE_CONFIG = { clientId, apiKey }`. It's committed to this repo — deliberately, since GitHub Pages has no build step to inject secrets at deploy time, and neither value is meant to be kept private: the Client ID only works from origins authorized in Google Cloud Console, and the API key is referrer- and API-restricted there (Picker API only). **A Client Secret must never go in this file or anywhere in this repo** — the client-side OAuth flow used here doesn't need one, and unlike the Client ID/API key it's a real credential worth protecting. (If you'd rather keep even these two values out of git history, `.gitignore` it again and inject at deploy time instead — e.g. a GitHub Actions secret written into the Pages workflow.) `.env.example` at the repo root mirrors the same two values for readers expecting that convention, but nothing in this static site actually loads a `.env` file — see the comment in that file.
- **Folder selection** uses the Google Picker API (`google.picker`, loaded via `gapi.load('picker', ...)`) rather than accepting an arbitrary pasted folder ID, specifically so `drive.file`'s minimal scope actually grants access to an existing folder the user didn't create through this app.
- **Sheet selection**: `connectExistingSheet(idOrUrl)` accepts a pasted Sheet URL or ID directly (the `spreadsheets` scope isn't creation-restricted the way `drive.file` is), or `createNewSheet()` makes one via the Sheets API. Either path calls `ensureHeaderRow()` to write the header row (`SHEET_HEADERS`: `Title, Category, Valuation, Disposition Status, Recipient, Drive Photo URL 1, Drive Photo URL 2, Drive Photo URL 3, Receipt URL 1, Receipt URL 2, Receipt URL 3, Logged At`) if it doesn't already match exactly. Each photo/receipt gets its own column, capped at `MAX_LINKED_MEDIA` (3) — deliberately *not* comma-joined into one cell, because Google Sheets only shows its hover-preview thumbnail when a cell's entire content is a single recognized Drive link; a comma-joined multi-URL cell isn't recognized as a link at all. `padUrls()` truncates/pads a URL list to exactly `MAX_LINKED_MEDIA` entries for the row array. `ensureHeaderRow()` enforces `SHEET_HEADERS` exactly (cell-by-cell comparison; rewrites the whole header row on any mismatch) for columns A through `sheetLastCol()`, but never touches anything beyond that, so custom columns a user added past the app's own schema are left alone — this is more assertive than a purely-additive approach because the column *meaning* has changed across schema versions (e.g. "Drive Photo URL" used to mean "first URL only", then "comma-joined all URLs", now "Drive Photo URL 1" of 3 separate columns), so old header text needs correcting, not just extending. It's called (cheaply, idempotently) at the top of every `appendOrUpdateSheetRow()`, so an older connected sheet self-upgrades on its next sync without the user needing to reconnect it — existing rows' *values* stay in their original columns when the schema only grows, but a column-meaning change like this one means old rows can end up mislabeled relative to the new headers; re-syncing an item rewrites its row correctly.
- **Upload**: `uploadFileToDrive()` builds a raw `multipart/related` body by hand (Drive's multipart upload format, not `FormData`) and POSTs to `https://www.googleapis.com/upload/drive/v3/files`. `uploadMediaList()` wraps it to walk either `asset.media` or `asset.receiptMedia`, skipping entries that already have a `driveUrl` and sharing one progress counter (`uploadState`) across both lists; receipts get `-receipt-<n>` in their filename to stay visually distinct from item photos in the Drive folder. All media uploads regardless of `MAX_LINKED_MEDIA` — the cap only affects what gets a sheet column, not what gets uploaded.
- **Sync orchestration**: `syncAsset(asset, onProgress)` uploads both `asset.media` and `asset.receiptMedia` (skipping anything already uploaded — re-syncing is incremental, not a full re-upload), then calls `appendOrUpdateSheetRow(asset, mediaUrls, receiptUrls)` — which **updates** the asset's existing row (tracked via `asset.sheetRow`, parsed from the Sheets API's `updates.updatedRange` response) if it has one, or appends a new row otherwise, so re-syncing an edited item doesn't create duplicate rows. It mutates the passed-in `asset` object in place (`media[]`/`receiptMedia[].driveFileId`/`driveUrl`, `sheetRow`, `driveSyncedAt`); callers (`app.js`) are responsible for `AssetDB.put(asset)` afterward. `isAssetSynced()` in `app.js` checks both media arrays for a `driveUrl` on every entry, not just `media`.
- **Delete cleanup**: `clearSheetRow(rowNumber)` blanks a row's cells (`values/{range}:clear`) rather than deleting the row outright — an actual row deletion would shift every row below it up by one, silently invalidating every *other* synced item's cached `sheetRow`. The `#modal-delete-btn` handler in `app.js` calls it best-effort — only when the asset has a `sheetRow` and `GoogleSync.isConnected()` is already true (never triggers an interactive OAuth popup from what should be a simple delete action) — and always proceeds with the local `AssetDB.delete()` regardless of whether the sheet clear succeeds, folding any failure into the one toast shown afterward rather than blocking deletion.
- **Backup upload**: `uploadBackup(blob, filename)` is a thin named wrapper around `uploadFileToDrive()` — same folder, same multipart mechanics — so the "Upload backup to Drive" button in `app.js` (in `renderGoogleSyncCard`'s connected state) can push the whole-catalog JSON backup into Drive without a separate code path. `app.js`'s `buildBackupBlob()` was factored out of the `btn-export-json` handler specifically so both the local-download button and this one always produce an identical backup from a single source of truth. Before uploading, that button checks `assets.filter(a => !isAssetSynced(a))`: if any are pending, a `confirm()` offers to sync them first via the shared `syncPendingAssets(onProgress)` helper (also used by `#google-sync-all-btn`, factored out specifically so both walk the same pending list the same way) — decline and it uploads immediately, accept and it syncs then uploads, and a sync error aborts the upload rather than proceeding next to an incomplete sync. Since `syncPendingAssets()` ends with `loadAssets()`, which re-renders this whole card, any button element reference held from before that call is stale afterward — the handler re-queries `container.querySelector('#google-upload-backup-btn')` post-sync rather than reusing the pre-sync reference (`container` itself, from `document.getElementById('google-sync-body')`, stays valid across the re-render since only its `innerHTML` is replaced, not the node itself).
- **Settings persistence**: folder ID/name and sheet ID/name/URL live in `localStorage` (`dostadning-google-sync`) — the OAuth access token itself is kept only in memory (`google-sync.js` module scope), never persisted, and is silently re-requested (falling back to an interactive prompt if silent refresh fails) via `getValidToken()` whenever a call needs one.
- **Not tested against a real Google Cloud project** — this was built without one (no way to create one autonomously) and only verified by mocking `window.GOOGLE_CONFIG`/`localStorage` to exercise the UI logic and error-handling paths. Verify against a real project before relying on it; if API behavior doesn't match what's coded here, Google's API may have changed since this was written.

## Running / testing

Serve the directory with any static file server (e.g. `npx serve .` or `python -m http.server`) and open the printed URL. Camera testing on a real phone needs an `https://` URL (deploy to GitHub Pages/Netlify/Vercel, or tunnel with `ngrok`/`localtunnel`) — see README.md for details. There is no build, lint, or test command.
